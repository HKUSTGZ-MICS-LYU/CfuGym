# Repository guide for coding agents

This file applies to the repository root. Consult the relevant source and current documentation before changing behavior; this is a map and a validation checklist, not a substitute for the code.

## What this repository contains

CfuGym is a VexiiRiscv/SpinalHDL hardware–software co-design workspace for MiCo, BitNet/BNCFU and custom function units (CFUs). Changes commonly span instruction decoding, CPU/SoC parameter wiring, accelerator RTL, RISC-V intrinsics/kernels, and simulator arguments.

- `src/main/scala/vexiiriscv/execute/`: execution plugins (for example `MiCoPlugin.scala` and `BitNetPlugin.scala`); `src/main/scala/vexiiriscv/soc/mico/`: SoC, CFUs, fibers, generator and simulator (`MiCoSocParam`, `MiCoSocGen`, `MiCoSocSim`). `src/test/scala/` contains Scala simulation/regression code.
- `sw/` is a **Git submodule** with bare-metal C/assembly, `MiCo-Lib`, targets and software tests. `sw/Makefile` owns `compile`/`recompile`; `sw/MiCo-Lib/targets/vexii_soc.mk` owns ISA/ABI, target sources, `OPT`, `VLEN`, quantization and memory options. Inspect its local status before editing and report submodule changes separately.
- `agents/` is the Python CFU design agent, with CLI `agents/run_cfu_agent.py`, implementation `agents/cfu_design_agent/`, policy `agents/specs/`, and `unittest` tests `agents/tests/`. Read `agents/README.md` before changing this system; it documents the current flow and agent-specific write boundaries.
- `skills/cfu-designer/` has CFU methodology, reference flows, examples and templates; start with `SKILL.md`, then read only the relevant reference. `tools/` holds BNCFU benchmark/exploration scripts; `docs/` holds project-specific design/experiment notes; `README.md`, `README_MICO.md` and `README_BNRV_SoC.md` give broader context.
- `ext/` (including SpinalHDL and RVLS), `benchmarks/embench-iot`, `benchmarks/PolyBenchC`, and `sw/` are submodules (`.gitmodules`). Do not edit vendored or submodule contents casually, and do not reset an existing dirty submodule.

## Working rules

1. Inspect `git status --short` and the status of affected submodules first; preserve unrelated staged, unstaged and untracked work. Prefer minimal, local edits. Do not commit generated results or silently rewrite third-party trees.
2. Keep the HW/SW contract together: custom opcode/`func3`/`func7`, operand values versus raw register IDs, CSR/enable behavior, response/backpressure, vector length, quantization and software intrinsics must agree. A SoC feature also needs the corresponding CPU parameter in `p.vexii`; the CPU CFU bus has one owner unless explicit arbitration is implemented.
3. For agent-generated designs, distinguish the **tracked** `AgentCfu.scala`/`AgentCfuFiber.scala` scaffolds and read-only `AgentCfuLib.scala` platform from the run-scoped copies under `agents/generated/runs/<run_id>/workspace/design/`. The design agent's policy confines its writes to the run workspace; do not bypass it by modifying tracked platform files on its behalf. For changes to the framework itself, follow `agents/README.md` and update focused tests.
4. Python agent responsibilities: `benchmark/` handles workload adapters; `flow/` owns the flow shape and the domain control plane (`wiring.py` node/edge layout, `gates.py` gate and budget helpers, `ladder.py` routing and repair decisions, `instrument.py` node instrumentation and fingerprinting, `optimize.py` the optimization ledger, `policies.py` the per-node LangGraph policies, `outcome.py` the gate/rewind vocabulary); `stages/` holds the stage logic, one module per stage (`context.py`, `profile.py`, `analysis.py`, `contract.py`, `implement/`, `verify/`, `review/`, `feedback.py`); `runtime/` owns execution services (policy, tools, artifacts, LLM, checks, commands, stage services, persistence, coding sessions); `state/` declares the run state in named groups (`config`, `evidence`, `ledger`, `optimization`) composed into `CfuDesignState`; `ir/` supplies optional LLVM IR evidence. `graph.py` is only the composition root — the public entry points plus the node functions `python_nodes()` resolves. Reach a function through its owning module (`from ..runtime import checks`, then `checks.run_check(...)`), never `from ..runtime.checks import run_check`: an imported name is a binding, so a test that mocks the owning module would not be observed. `graph.py` re-exports only public entry points and node functions, so a stale `mock.patch.object(graph, "<helper>")` fails loudly instead of silently patching a binding nobody reads. Preserve existing public imports and test patch points; avoid putting benchmark-specific mechanics in the common graph runner. LLVM IR is static evidence, not measured cycles.
5. Keep generated `*.v`, ELF/ASM, `target/`, `simWorkspace/`, `benchmark_results/`, `synth_runs/` and `agents/generated/` out of ordinary source edits. Check whether a result path is tracked before cleaning or overwriting it. Several generated RTL/log files already exist in this checkout.

## Validation by change type

Run commands from the repository root unless indicated. Only report a command as passing when it actually ran here; missing tools, skipped simulations and environment failures must be stated explicitly.

- **Python agent behavior:** `python3 -m unittest agents.tests.test_module_layout` for a focused smoke check; use `python3 -m unittest agents.tests.test_<area>` for the changed module. When dependencies (`openai`, PyYAML, etc.) and an appropriate disposable artifact workspace are available, run `python3 -m unittest discover -s agents/tests -t . -p 'test_*.py'` for broader coverage. Some tests create/remove fixed paths under `agents/generated/runs/`; check for existing run artifacts first. These tests use `unittest`, not `pytest`; the project documentation uses `conda run -n mico_env` when the base interpreter lacks dependencies. The suite is deliberately a **fast contract suite** (target <= 30 s): add coverage at the router/unit level, and do not add another full-ladder integration scenario — one end-to-end smoke run (`test_graph_smoke.py`) plus the routing decision table (`test_graph_routing.py`) already cover the flow.
- **Scala/SpinalHDL:** use an environment with sbt/JDK and start with `sbt compile`; for test-source edits use `sbt 'Test / compile'` before choosing a focused `sbt 'testOnly <suite>'`. Do **not** use the full `sbt test` as a quick smoke check: it runs substantial regression/simulation work. The sbt build defaults to `SPINALHDL_FROM_SOURCE=1`, uses `ext/SpinalHDL` and its IDSL compiler plugin, and accepts `SPINALHDL_PATH`; `build.mill` is an alternative, but the existing SoC scripts use sbt. For parameter/wiring changes elaborate with `sbt 'runMain vexiiriscv.soc.mico.MiCoSocGen <soc args>'` or inspect `gen_soc.sh`. Generation writes root-level Verilog and `soc.h`; avoid overwriting existing outputs. For isolated AgentCfu RTL generation, `GenAgentCfu --out-dir <DIR>` accepts a separate output directory.
- **Bare-metal software:** after confirming the RISC-V cross-compiler is available, e.g. `make -C sw recompile MAIN=tests/<test_name> TARGET=vexii_soc MARCH=rv32imc OPT=cfu SPRAM=1`. Choose `MAIN`, `MARCH`, `OPT`, `VLEN`, `BITNET_QUANT` and `USE_SIMD` from the particular test and matching hardware; this line is a template, not a universal build. See `README_BNRV_SoC.md` for concrete BNRV variants.
- **End-to-end correctness:** run a scalar/reference comparison and simulate its actual ELF with matching SoC flags, e.g. `sbt 'runMain vexiiriscv.soc.mico.MiCoSocSim --load-elf <elf> --with-rvc --with-rvm --with-rdtime <soc args>'` or an appropriate `sim_soc*.sh`. The software ISA/ABI, CPU extension flags, CFU configuration and memory setup must match; counter instructions need counter hardware. Custom instructions may require `--no-rvls-check`. Do not infer speedup from a successful compile or functional pass.
- **Performance/cost changes:** retain exact commands and parameters, scalar/CFU results, cycle/profile evidence and the synthesis basis. Consult `skills/cfu-designer/references/validation-flow.md` and `yosys-cost-flow.md`; Yosys estimates should use generated standalone/SoC hardware RTL, not simulator RTL. Run full simulations and synthesis only when warranted by the task and tools available.

The Python design-agent CLI does not edit source or execute build commands by default; `--apply-patch` and `--run-commands` explicitly enable their respective allowlisted effects. Even `--dry-run` creates run artifacts under `agents/generated/runs/<run_id>/`, so choose a unique run ID and inspect existing outputs first. A planned run is not a validated design. Before launching one, read its CLI options and `agents/README.md` so a planning task does not inadvertently start toolchain-heavy generation, simulation or cost stages.
