# Custom workloads (Embench-compatible)

Workloads in this directory are **not** part of `benchmarks/embench-iot`. They
exist to exercise a class of acceleration that a compiler-style, IR-driven CFU
design is structurally unable to see: the sources are written the way real
embedded C is written, so the property that makes a custom unit worthwhile — the
*meaning* of the variables — is already gone by the time the code reaches LLVM
IR.

Each workload implements the Embench benchmark interface exactly, so the CFU
design agent's Embench adapter prepares it unchanged: same workspace copy into
three configurations (`reference`, `profile`, `cfu`), same instrumentation, same
`EMBENCH_VERIFY_*` oracle line, same `CFU_AGENT_PROFILE` cycle table, same
`sw/embench` board and `sw/MiCoLib` build.

The two motivating examples of that semantic loss are `popcount` (an `int32`
whose C form is a chain of shifts, masks and adds, so the code never says "count
the set bits") and BitNet packed ternary × int8 matmul (`int1.58` weights arrive
as bytes of 2-bit codes, so the code never says "multiply by -1, 0 or +1").
Both are implemented here as full workloads, and four further routes to the same
loss are added, so six different kinds of information loss are covered:

| Workload | Route by which the semantic survives in C but dies in IR |
| --- | --- |
| `gf-erasure` | The algebra is **in the table data**. `a*b` in GF(2^8) is two loads from `log[]`/`exp[]`; nothing in the IR says "finite field". |
| `median3x3` | The operator is a **comparator network**, but the sort is data-dependent control flow, so the IR splits it across basic blocks and never shows one 9-input function. |
| `varint-delta` | The operation has a **runtime-determined width**. A variable-trip-count `do/while` hides a fixed-width combinational decode whose length is in the data, not in the type. |
| `popcount-hamming` | The variable is a **set of flags, not a number**. A 32-bit word carries 32 independent bits; counting them is a byte-table load (or a SWAR trick), and the search that consumes the counts is not a reduction the compiler can see. |
| `bitnet-ternary` | The **datum is not of its type**. Weights are ternary, packed four to a byte (2 bits each) at export time; the kernel dissolves the format into `& 3` / `- 1` / multiply, so `× {-1,0,+1}` survives as a real multiply of an `int32` by an `int8`. |
| `ntt` | The **arithmetic is a finite field**. Every value is a residue mod 3329, but the source only says `% 3329`; the IR sees a magic-number multiply (`mulhu`), and nothing marks the operands as field elements or the multiplier as a twiddle rotation. |

That is the whole point of this directory: a popcount-style loss is not the only
one, and each route implies a different CFU shape and a different ISA contract
(lane width, state, and whether the instruction is a value or a stream).

## Interface contract

A workload is one directory `benchmarks/custom/src/<name>/` containing one or
more `.c` files. The framework copies `<name>` into
`<run>/workspace/embench_<name>/{reference,profile,cfu}/src/` and compiles it
with Embench's `support/main.c`, `support/beebsc.c` and `sw/embench/board`.

Required, enforced by `agents/cfu_design_agent/benchmark/embench_integrity.py`:

- `#include "support.h"` and the four Embench entry points:
  `initialise_benchmark()`, `warm_caches(int)`, `benchmark()`,
  `verify_benchmark(int)`. These names are **reserved**: the agent may not
  define, shadow or replace them, so inputs, scaling, timing and the oracle stay
  host-owned.
- Exactly one `#define LOCAL_SCALE_FACTOR N` in the whole source set. The
  harness rewrites it to `1` (`cold_single_invocation_v1`), so the code must do
  enough work in **one** `benchmark_body(1, 1)` pass; the factor only matters for
  `warm_caches` runs.
- The usual Embench shape: `benchmark()` → `benchmark_body(lsf, gsf)`, with the
  hot kernel `noinline` so it appears in the profile table.
- Inputs are built in `initialise_benchmark()`, never from `argv`, `time()` or
  `rand()` (the run must be deterministic).
- `verify_benchmark()` must check the **produced output**, not only the returned
  `int`. Return non-zero only when everything is correct; every workload here
  also compares against a golden digest constant so a plausible-looking but
  wrong kernel cannot pass.
- Do not define `main`, `memcmp`, `memcpy`, `memset`, `memmove`, or a symbol that
  shadows one. Do not use `__attribute__((section/constructor/...))`.
- Integer code only on the `rv32imc` target; keep the working set well under the
  board's 64 KiB heap and the SoC's 256 KiB RAM.

A workload's data is generated by itself, so the *only* thing a new workload
must get right by hand is the golden constant; recompute it from the scalar
build (see "Recomputing a golden value" below).

Note that this file is deliberately **outside** the agent's readable tree
(`agents/specs/agent_access_policy.yaml` allows `benchmarks/custom/src/**`
only): the model must derive the semantic function of a workload from the
profile and the C source, not from a design note that names the acceleration for
it.

## `gf-erasure` — Reed-Solomon erasure coding over GF(2^8)

`src/gf-erasure/gf_erasure.c`

**Where this runs in the real world.** Every storage or transport system that
survives loss without retransmitting: object stores and distributed filesystems
implementing Reed-Solomon (Ceph, MinIO, HDFS-3 erasure coding, Backblaze Vaults,
Azure LRC), RAID-6 and ZFS `raidz2` double parity, NAND/UFS/eMMC flash
controllers that code across dies, optical/DVB-S2/DSL FEC, CCSDS deep-space
links, and QR/PDF417/DataMatrix barcodes — all of them are GF(2^8) arithmetic
and nothing else. On a gateway or a camera, the shard sizes are small and the
codec runs per block, which is exactly this benchmark's shape.

**Shape.** K = 8 data shards, M = 4 parity shards, 256 B per shard, systematic
generator `[I ; C]` with a Cauchy matrix `C[i][j] = 1/(x_i ^ y_j)` (any 8 of the
12 rows stay invertible, i.e. the MDS property). One invocation:

1. encode `parity = C · data` (4·8·256 = 8192 field multiplies),
2. lose shards 2 and 5, take the first 8 survivors, invert their generator rows
   with Gauss-Jordan over GF(2^8),
3. rebuild the two lost shards from the survivors (2·8·256 = 4096 multiplies).

`LOCAL_SCALE_FACTOR 4`, so ~49k field multiplies per measured run.

**What the compiled code looks like.** `gf_mul(a, b)` is
`a == 0 || b == 0 ? 0 : gf_exp[gf_log[a] + gf_log[b]]`: a zero-test branch and
two byte loads from `static` arrays, per multiply. The inner loop is
`acc ^= gf_mul(coef[j], src[j][i])` — in IR: load, branch, load, load, add, load,
xor. Nothing distinguishes this from arbitrary table-driven arithmetic, and the
fact that the two tables describe a field (and that `log[a] + log[b]` is a
modular add mod 255) is not recoverable from the ops; it lives in `gf_log`
contents, which the pass never reads.

**CFU opportunity.** One instruction per packed byte group: a byte-wise
`acc ^= coef ⊗ src[i..i+3]` over four lanes, with the field multiply done
combinatorially (8×8 partial products reduced by the 0x11D polynomial) instead of
two dependent table loads. The dependency chain and the D-cache traffic both
disappear, and the four-lane form is exactly what the `for i` loop already does
across `i`. A second instruction (`row_accumulate`) can absorb the `j` loop, so
one call does a whole shard row. Decode needs nothing extra: it is the same
primitive with a different coefficient matrix, which is why a semantic reading of
the code and a syntactic one lead to different datapaths (LUT vs. combinational
lanes).

## `median3x3` — 3×3 median filter for an 8-bit frame

`src/median3x3/median3x3.c`

**Where this runs.** Camera and sensor pipelines before anything else touches
the frame: ISP denoising of impulse ("salt-and-pepper") noise from low-cost CMOS
sensors and thermal arrays, machine-vision front ends (OpenMV-class boards,
industrial inspection), automotive image preprocessing, and the same kernel in
medical/ultrasound and display-defect imaging. The 3×3 median is also a building
block of max-median-min filtering used in demosaicing and edge detection, so it
is rarely the last stage.

**Shape.** A 64×32 grayscale frame with ~10 % impulse noise (40–60 % of the
dynamic range, not a token few pixels). Borders are passed through; each of the
62·30 = 1860 interior pixels sorts its 3×3 neighbourhood with an insertion sort
and keeps `w[4]`. `LOCAL_SCALE_FACTOR 2`.

**What the compiled code looks like.** The sort is a nested `do/while` with a
data-dependent inner trip count: the IR is a nest of basic blocks with a
back-edge whose exit depends on the pixel values. The median as a value — the
output of a fixed 19-comparator network, or of three column sorts plus a
diagonal step — does not exist anywhere in the IR; nor does the fact that
neighbouring outputs share six of nine inputs (`x` slides the window by one
column per iteration). An IR-level fusion pass sees a loop with a conditional
inner loop; a workload-aware designer sees "output pixel = median of a 3×3
window, and the window is a sliding buffer".

**CFU opportunity.** Byte-wise `min`/`max` with a 19-comparator median network,
plus three columns held in the unit's own registers: each `x` step pushes one
new 3-byte column (three loads) and pops the median (one register). That turns
~9 loads + up to 36 compare-exchange operations per pixel into 3 loads + 1
result, and it is only expressible this way if the designer knows the
*streaming* nature of the filter — the sharing across iterations is not a
statement in the source, only a consequence of the filter's meaning.

## `varint-delta` — LEB128 + ZigZag delta telemetry decoding

`src/varint-delta/varint_delta.c`

**Where this runs.** Any application that reads packed time series or protobuf:
protobuf `sint32/sint64` with packed repeated fields and ZigZag, MQTT remaining
length, Avro, WebAssembly and DWARF LEB128, and time-series engines that pack
delta-encoded samples as varints (Gorilla-style blocks, Prometheus remote write,
InfluxDB TSM, Cassandra 3.0 `VIntCInt`). On the device side it is the decoding
half of a sensor gateway: a radio frame arrives as opaque bytes and becomes
`int32` samples.

**Shape.** Four channels × 1024 samples, encoded at initialisation as
delta → ZigZag → base-128 varint:

| channel | signal | stream bytes | varint widths |
| --- | --- | --- | --- |
| 0 | temperature, centi-degrees, ±3 steps | 1024 | 1024 × 1 B |
| 1 | accelerometer triangle wave + noise | 1747 | 301 × 1 B, 723 × 2 B |
| 2 | timestamps, 10 ms + jitter | 3072 | 1024 × 3 B |
| 3 | counter, occasional resets / large jumps | 1102 | 1004 × 1 B, 2 × 4 B, 18 × 5 B |

6945 bytes per pass, `LOCAL_SCALE_FACTOR 8`. The mixed widths are the point: a
single-channel 1-byte stream would let the compiler constant-fold the
`do/while` away.

**What the compiled code looks like.** In IR the decoder is a
`do { b = *p++; v |= (b & 0x7F) << shift; shift += 7; } while (b & 0x80)` loop
with an unbounded trip count, followed by a ZigZag fixup and a running prefix
sum. Every `shl`/`or` looks like generic bit manipulation; the operand order
(LSB group first), the maximum of 5 groups, the fact that the terminator bit
*is* the length and that the 7-bit groups must be concatenated with no gaps —
all of that is implicit in the control flow, not in the dataflow the IR exposes.

**CFU opportunity.** A fixed-width decode of a variable-width value: given a
32- or 64-bit word, find the first byte without the continuation bit
(leading-one/clz over the masked word gives the boundary), compute the number of
7-bit groups, compress them into a value (a `pdep`-style bit gather), then apply
ZigZag and the delta add — one instruction returning the value *and* the number
of bytes consumed, or a streaming variant returning up to four samples per call
(the published SIMD technique for posting-list and protobuf decoding, which only
works because the ISA designer knew the encoding). Note the two instructions
differ in interface, not in arithmetic: one is `value + consumed`, the other is a
refill-and-drain stream, and choosing between them is a semantic decision the IR
cannot make.

## `popcount-hamming` — nearest-signature search over binary fingerprints

`src/popcount-hamming/popcount_hamming.c`

**Where this runs.** Everywhere a 512-bit signature stands for a record:
near-duplicate and near-image detection over simhash/LSH codes, binary
embeddings in vector search, bitmap-index cardinality in analytical engines
(Roaring/EWAH), BCH and LDPC decoding, packet-mask classification, chess
bitboards, and Hamming-distance sketches. The operation is always the same:
XOR two words, count the set bits of the difference, accumulate.

**Shape.** 16 clusters of 16 signatures, 16 words (512 bits) each — a
deduplicated corpus looks like this: tight near-duplicate clusters (members a
few bits apart, ~255 bits of the 512 between clusters). The query is a perturbed
copy of one member; every signature is scanned, minimum distance and the number
of hits inside a 200-bit radius are reported. `LOCAL_SCALE_FACTOR 4`.

**What the compiled code does.** The bit count is a 256-byte table:
`pop8[d & 0xFF] + pop8[(d >> 8) & 0xFF] + ...`, so the IR is XOR, four shifts,
four masked loads and three adds — no `ctpop`, and nothing that says the operand
is a set. The SWAR form (`x - ((x >> 1) & 0x5555...)` …) is not a fix either:
built for `rv32imc`, GCC 15 emits the SWAR sequence literally (22 instructions,
no libgcc call) and Clang keeps it too (21 instructions, and still no `cpop`
under `-march=rv32imc_zbb`), so the information dies twice: the type says
`int32`, and the target has no way to accept a bit count even when the source
spells one out.

**CFU opportunity.** A 32-bit popcount primitive is the obvious unit; the
workload-aware version is better: `hamming4(a, b)` returning the popcount of four
XORed word pairs in one shot (four 32-bit adds feeding one 7-bit accumulator),
which is exactly the shape of the inner loop, and a scan instruction that folds
`min`/`hits` accumulation so the loop body becomes one instruction per signature
instead of 16. The unit is trivially small (a 4:2 adder tree of 32 full adders)
and its value comes entirely from recognizing the *search*, not from the
arithmetic — which is why an IR-level fusion pass, which sees only loads and
adds, cannot price it.

## `bitnet-ternary` — BitNet b1.58 ternary-weight × int8 matmul

`src/bitnet-ternary/bitnet_ternary.c`

**Where this runs.** On-device LLM and tiny-ML inference with ternary weights:
BitNet b1.58 (Microsoft Research) and the ternary-weight networks that preceded
it, plus the "1.58-bit" quantization path that embedded inference engines use to
fit a transformer layer into a few hundred kilobytes. The repo's own
BitNet/BNCFU path is the hardware counterpart of this benchmark.

**Shape.** 32 output rows × 120 input columns × 16 activation vectors. The
weights are packed **offline**, at quantization/export time, in the `I2_S`
layout used by bitnet.cpp: two bits per weight, four weights per byte, codes
`{0,1,2}` for `{-1,0,+1}` (code 3 unused) — 30 bytes per row. Activations are
`int8`, accumulators `int32`, then a per-row integer re-scale and saturation back
to `int8`. 61,440 ternary MACs per pass, `LOCAL_SCALE_FACTOR 2`. The packer in
`initialise_benchmark()` stands in for the export-time quantizer and runs
outside the timed region, exactly like loading a model file from flash.

**Why this packing, and what the industry does with it.** Three layouts ship
today, and they sit at different points on the same axis:

| Layout | Storage | What the kernel does per weight |
| --- | --- | --- |
| `I2_S` | 2 bits, 4 per byte | unpack (`& 3`, `- 1`) and multiply — this benchmark |
| `TL1` | 2 bits grouped in pairs | the 4-bit code *is an index* into a table of activation partial sums |
| `TL2` | 1 sign bit + 4-bit mirrored index (1.667 bpw) | same, three weights per index, sign applied by mirroring |

TL1/TL2 (the lookup-table kernels of
[bitnet.cpp](https://arxiv.org/abs/2502.11880), building on T-MAC) avoid the
multiply by precomputing, per block, the partial sums of the *activations* and
using the weight code as an index; the weight is never unpacked into a scalar.
`I2_S` is the portable lossless baseline this benchmark measures, because it is
the form in which the loss is most visible.

**What the compiled code does.** Per weight: `(code >> 2t) & 3`, subtract one,
multiply by the activation. Compiled for `rv32imc` that is `andi` + `mul` (eight
`mul`s in the unrolled body), i.e. 61,440 real multiplications where a ternary
unit would need none. Nothing in the IR says the multiplier's left operand is
three-valued, so no pass can turn `w * x` into a conditional add/subtract; the
packed format has been dissolved into per-weight scalar arithmetic, which is
also why the load count is four times what the format implies.

The packing is storage, not semantics: re-pack the identical trit sequence from
a five-trits-per-byte base-3 layout into `I2_S` and the output digest does not
change — only the code that reads it does. (A portable base-3 decoder written as
`code % 3; code /= 3` compiles to `lui 0xaaaab` plus a `mulhu`/`srli` chain, i.e.
magic-number division: the far end of how much the representation can drift from
the arithmetic it stands for. Nothing ships that way, but it is what "the type is
`int32`" costs when the decompressor is written in software.)

**CFU opportunity.** For `I2_S`, one instruction per packed byte:
`ternary_dot(byte, x[0..3])` decodes the four 2-bit codes as select/add/subtract
against four activations, so the weight never becomes a value. For the
lookup-table layouts, the CFU needs no table at all: the same instruction applied
to a 64-bit operand covers 32 weights, and the adder tree that software builds as
a 16- or 243-entry table is simply the datapath. Either way the win is that the
*stored* format is the operand format — which is the one thing an ISA without a
ternary type can never express, and the reason the IR-level view (values,
multiplies) prices this kernel wrong.

## `ntt` — number-theoretic transform over Z_3329 (CRYSTAL-Kyber)

`src/ntt/ntt.c`

**Where this runs.** Every lattice scheme standardized or deployed today is
built on a 256-point NTT over a small prime field: CRYSTAL-Kyber (ML-KEM) and
its TLS 1.3 / SSH hybrid handshakes, Dilithium signatures, and the
microcontroller key-exchange paths that run them in a few hundred kilobytes.
The transform is what makes lattice crypto affordable: it turns the O(n²)
negacyclic polynomial multiplication into 896 butterflies, and it is the single
hottest kernel of key generation and encapsulation.

**Shape.** `q = 3329`, `n = 256`, primitive root `zeta = 17`, seven radix-2
stages, twiddle factors from a 128-entry table (the Kyber reference ordering,
`PRE_COMPUT_TABLE_NTT[k] = 17^bitrev7(k) mod 3329`), 896 butterflies per
transform. Each butterfly is one modular multiply and two modular adds, all
reduced by `% 3329`. `NTT_POLYS = 8` independent polynomials per pass,
7,168 butterflies, `LOCAL_SCALE_FACTOR 1`. Inputs are drawn once from an LCG,
and every measured pass transforms a fresh copy, so the result does not depend
on how many warm-up passes ran.

**Provenance.** A faithful port of the `pure_ntt()` kernel published with APS
(ICCAD'25, Sec. VI-C — the post-quantum case study whose Butterfly ISAX is
compared against this scalar form): same five-deep loop nest, same
`t`/`m`/`i`/`j1` index arithmetic, same `PRE_COMPUT_TABLE_NTT[m + i]` lookup, same
16-bit coefficients, same `% 3329` reductions. Two deliberate deviations:

- **`volatile` is dropped.** APS declares the array `volatile uint16_t *`
  because its compiler maps the accesses onto CADL `_mem[]` reads and writes.
  Keeping that qualifier here would compare a memory-clobbered loop against a
  CFU rather than an optimized scalar baseline.
- **eight polynomials per pass.** Each `ntt_256()` call is one 256-point
  transform, byte-for-byte the kernel above; the batch only reaches a
  measurable window. Per-transform cost is the reported total divided by 8.

The port is checked against `pq-crystals/kyber` `ref/ntt.c`: after converting
the reference's Montgomery domain (`fqmul`, `zetas[]`) to plain residues, all
256 coefficients agree for 200 random polynomials.

**What the compiled code does.** Per butterfly the IR is a load, a multiply, a
magic-number division for each of the three `% 3329` reductions, two adds, two
subtracts and two stores. Compiled for `rv32imc` with `-O3`, GCC emits
**zero** `remu`/`divu` and 10 `mul` plus 4 `mulhu` for the whole kernel: the
reduction became `mulhu`-by-0x3afb78b7-and-shift, which is a correct but opaque
way to reduce mod a prime, and it destroys the one fact a datapath would want —
that the multiplier's operand is a twiddle factor and the result lives in
Z_3329.

**CFU opportunity.** The natural unit is `modmul(a, b)`: two 16-bit residues in,
one out, Barrett reduction instead of the magic-multiply chain — exactly the
two-in/one-out shape of `CfuBus`. The better unit is the whole butterfly,
`bf(a, b, zeta)` returning `(a + zeta*b, a - zeta*b) mod q`: both results are
below 3329, so they pack into one 32-bit response and still fit the
single-output bus, while the twiddle table stays in memory and is read by the
scalar loop. That is APS's Butterfly ISAX, and the vectorized variant they call
Butterflyx2 is the same instruction twice per call with a 64-bit operand.

**Measured so far.** The agent's own simulation configuration (`MiCoSocSim`
with `--system-frequency 100000000 --with-rvc --with-rvm --with-rdtime
--mico-agent-cfu --agent-cfu-bus-width 32 --agent-cfu-no-load
--agent-cfu-no-store --agent-cfu-no-tilelink`, no `--sparse-mem`) reports
`CFU_AGENT_PROFILE ntt=1104578` for the `profile` build and
`EMBENCH_VERIFY_PASS benchmark=ntt verify=1`, i.e. **138,072 cycles per
256-point transform** (8 transforms per `benchmark()` call). The `reference`
build under `--sparse-mem` reports 1,112,628 (139,078 per transform). APS reports 76,955
(Croc) and 112,328 (Rocket) for the same transform. The same order of magnitude
on a different core is the expected outcome, not a claim of equivalence; a
comparison should re-run both sides' baselines.

## Running a custom workload

Host sanity check (no simulator, uses the Embench support code):

```sh
gcc -O2 -I benchmarks/embench-iot/support \
    -D GLOBAL_SCALE_FACTOR=1 <host_harness.c> \
    benchmarks/embench-iot/support/beebsc.c
```

with `<host_harness.c>` calling `initialise_benchmark()`, `benchmark()` and
`verify_benchmark(result)` and stubbing the three board hooks.

Cross-compile the way the framework does (`reference` configuration; the agent
adapter additionally builds `profile` and `cfu`):

```sh
make -C sw TARGET=vexii_soc MARCH=rv32imc_zicsr_zifencei \
  MAIN=<run>/workspace/embench_gf-erasure/reference/embench_main \
  BUILD=<run>/workspace/embench_gf-erasure/reference/build \
  EXTRA_SOURCES="<run>/workspace/embench_gf-erasure/reference/src/*.c \
                 <run>/workspace/embench_gf-erasure/reference/support/beebsc.c \
                 <run>/workspace/embench_gf-erasure/reference/board/boardsupport.c" \
  EXTRA_INCLUDES="<run>/workspace/embench_gf-erasure/reference/support \
                  <run>/workspace/embench_gf-erasure/reference/board" \
  EXTRA_CFLAGS="-DHAVE_BOARDSUPPORT_H -DWARMUP_HEAT=1 -DGLOBAL_SCALE_FACTOR=1 \
                -DEMBENCH_NAME=gf-erasure" \
  compile
```

Run the agent:

```sh
python3 agents/run_cfu_agent.py --embench gf-erasure \
  --max-iters 5 --conformance-mode dev --run-id <unique-id>
```

The Embench adapter resolves the name against `benchmarks/embench-iot/src`
first and `benchmarks/custom/src` second, so `--embench` accepts either suite;
the run's `04_benchmark/embench.yaml` records `suite: custom` for these. Plan
without touching toolchains or an API key with `--dry-run`.

Verified so far:

- all six pass `verify_benchmark` on the host with `-O0`, `-O1`, `-O2` and
  `-Os` (identical result and digest at every level);
- all six cross-compile for `rv32imc_zicsr_zifencei` with the Embench support
  code and the `sw/embench` board (34–37 KB ELF for the first five, ~41–54 %
  of 256 KiB RAM; `ntt` links to a 113 KB RAM image, 43 %, in the same range);
- `ntt` is the only one with a measured cycle count so far: `MiCoSocSim
  --sparse-mem` reports 1,112,628 (`reference`) / 1,104,578 (`profile`) cycles
  for one `benchmark()` call, i.e. ~138 k per 256-point transform, and
  `EMBENCH_VERIFY_PASS` on the SoC. For the others, take the count from a
  run's `reference`/`cfu` simulation, not from a compile.

## Recomputing a golden value

The `EXPECTED_RESULT` constant is the FNV-1a-32 digest of the workload's output
after one `benchmark_body(1, 1)` pass (`popcount-hamming` additionally pins
`EXPECTED_DIGEST` for its corpus, because its result binds the scan and the
corpus separately). If you change the kernel or the input
generation, rebuild with the host harness above and read the printed result; a
mismatch is a failure, not a new golden value, unless you have a reason to
believe the scalar path changed.

## Adding another workload

1. `mkdir benchmarks/custom/src/<name>` and add `<name>.c` with the interface
   above; keep it single-file unless the algorithm needs more.
2. Put the noisy, realistic thing in `benchmark_body`; make the kernel
   `noinline` and do enough work per pass (tens of thousands of cycles on
   `rv32imc` is a reasonable target for a cold single invocation).
3. Choose an angle: what does the C source know that the IR will not? If the
   answer is "nothing", the workload does not test the framework's advantage —
   use an existing Embench benchmark instead.
4. Compute the golden constant from the scalar build, then confirm
   `verify_benchmark` returns non-zero and that the three configurations build.
